1项目概述

Frostmourne（霜之哀伤）是汽车之家经销商技术部监控系统的开源版本，定位为通用数据监控报警平台。其核心理念是："只需写一条数据查询，即可完成监控配置"。

解决什么问题

团队建立 ELK 日志体系、Prometheus 指标体系后，往往缺乏配套的监控报警方案。初期使用 ElastAlert 存在管理成本高、稳定性不足等问题，Frostmourne 正是为了填补这一空白而诞生——用更易用、更稳定的方式做数据监控。

核心能力一览

数据源丰富
支持 Elasticsearch、Prometheus、SkyWalking、InfluxDB、MySQL、ClickHouse、SqlServer、IoTDB、HTTP、PING、Telnet 共 11 种数据源类型
灵活报警
钉钉、企业微信、飞书、OneMessage 机器人、邮件、短信、HTTP POST 共 7 种消息发送方式
智能抑制
报警静默、报警升级、恢复通知、消息允许发送时段控制，防止消息轰炸
模板引擎
Freemarker 模板定制报警内容，支持变量占位符；消息格式支持 Text 与 Markdown
分布式调度
内置类 xxl-job 思想的调度引擎，每个监控独立调度互不影响，支持快慢线程池
权限隔离
部门-团队-用户三级组织模型，数据隔离，各团队互不影响；支持 LDAP 认证

入口：AlarmService.run()

整个链路的编排者在 AlarmService 中，核心方法 run(AlarmContract, boolean test) 的执行逻辑：

// 1. 根据规则类型找到对应的 IRule 实现
IRule rule = ruleService.findRule(alarmContract.getRuleContract().getRuleType());

// 2. 根据数据源类型 + 指标类型找到对应的 IMetric 实现
DataSourceType dataSourceType = ...;
IMetric metric = metricService.findMetric(dataSourceType, metricContract.getMetricType());

// 3. 组装执行器并执行（拉取指标 + 规则判定）
AlarmExecutor alarmExecutor = new AlarmExecutor(alarmContract, rule, metric);
AlarmProcessLogger alarmProcessLogger = alarmExecutor.execute();

// 4. 报警判定（连续次数、静默检查）
boolean isAlert = VerifyResult.TRUE.equals(alarmProcessLogger.getVerifyResult())
                    && judgeAlert(alarmProcessLogger);

// 5. 渲染报警消息（Freemarker 模板）
if (isAlert) {
    String completeMessage = completeAlertMessage(alarmContract, alarmProcessLogger, rule);
}

// 6. 非测试模式：记录日志 + 触发报警发送
if (!test) {
    updateAlarmLastExecuteInfo(...);
    alertService.alert(alarmProcessLogger);  // 进入报警发送流程
}
设计亮点：策略模式贯穿全程 IRule（规则策略）、IMetric（指标策略）、MessageSender（发送策略）均以接口形式定义，通过 *Service.findXxx() 动态查找实现。新增数据源或报警方式只需新增实现类，符合开闭原则。

6调度子系统

调度引擎位于 schedule 包，借鉴 xxl-job 思想自研，是整个系统的"心脏"。核心由两个守护线程 + MySQL 行锁实现分布式调度。

核心组件

组件职责
JobScheduleHelper调度核心：scheduleThread（预读线程）+ ringThread（时间环触发线程）
JobTriggerHelper触发核心：快慢双线程池（fastTriggerPool / slowTriggerPool），超时任务自动降级到慢池
CronExpressionCron 表达式解析，计算下次触发时间
RemoteTriggerService远程触发服务，实际调用 AlarmService 执行监控
TaskComponent任务组件，管理调度生命周期
job_lock 表数据库锁表，select ... for update 实现分布式互斥

调度流程详解

/** scheduleThread 主循环 **/
while (!scheduleThreadToStop) {
    // 1. 获取数据库行锁（for update），保证分布式环境下只有一个实例调度
    conn.prepareStatement("select * from job_lock where lock_name='schedule_lock' for update");

    // 2. 预读未来 5 秒内待执行的监控任务（PRE_READ_MS = 5000）
    List<Alarm> scheduleList = alarmRepository.querySchedule(nowTime + 5000, 1000);

    for (Alarm alarm : scheduleList) {
        if (超期 > 5s) {
            // misfire：立即补偿触发一次 + 计算下次时间
            JobTriggerHelper.trigger(alarm.getId());
            refreshNextValidTime(alarm, now);
        } else if (已到期) {
            // 立即触发 + 计算下次时间
            // 若下次触发仍在 5 秒内，放入时间环
            JobTriggerHelper.trigger(alarm.getId());
            pushTimeRing(ringSecond, alarm.getId());
        } else {
            // 预读：放入时间环（按秒分桶）
            pushTimeRing(ringSecond, alarm.getId());
        }
    }

    // 3. 更新 alarm 表的 trigger_last_time / trigger_next_time
    // 4. 提交事务，释放行锁
    // 5. 休眠对齐到下一秒
}

/** ringThread 主循环：每秒扫描时间环 **/
while (!ringThreadToStop) {
    // 取当前秒 + 上一秒的任务（避免处理耗时跨刻度漏触发）
    for (int i = 0; i < 2; i++) {
        List<Long> jobs = RING_DATA.remove((nowSecond + 60 - i) % 60);
        for (Long jobId : jobs) {
            JobTriggerHelper.trigger(jobId);  // 丢入线程池异步执行
        }
    }
}

快慢线程池机制

智能降级设计 JobTriggerHelper 维护两个线程池：快池（fastTriggerPool）和慢池（slowTriggerPool）。若某个监控任务在 5 分钟内超时（>5s）超过 15 次，自动降级到慢池执行，避免慢任务拖垮快任务调度。这是非常精妙的资源隔离设计。

执行器（AlarmExecutor）

AlarmExecutor 是单次监控执行的编排者，组合了 AlarmContract（配置）、IRule（规则）、IMetric（指标）三个策略：

public AlarmProcessLogger execute() {
    alarmProcessLogger.trace("execute start");
    alarmProcessLogger.setStart(DateTime.now());

    // 调用规则判定：内部会先 metric.pullMetric() 拉数据，再做阈值比较
    ExecuteStatus executeStatus = doRule();
    alarmProcessLogger.setExecuteStatus(executeStatus);

    alarmProcessLogger.trace("execute end");
    alarmProcessLogger.setEnd(DateTime.now());
    return alarmProcessLogger;
}

private ExecuteStatus doRule() {
    try {
        boolean verifyResult = rule.verify(logger, ruleContract, metricContract, metric);
        logger.setVerifyResult(verifyResult ? VerifyResult.TRUE : VerifyResult.FALSE);
        return ExecuteStatus.SUCCESS;
    } catch (Exception ex) {
        logger.trace("error: " + ex.getMessage());
        return ExecuteStatus.ERROR;
    }
}

9报警与消息发送

报警处理（AlertService）

AlertService 负责报警的完整生命周期管理，核心逻辑包括：

  • 报警判定：连续报警次数达阈值（ALERT_CONDITION）才真正报警
  • 静默检查：基于 alert_event 表和静默表达式，判断是否处于静默期
  • 恢复通知：上次报警、本次未报警时，发送 RECOVER 恢复消息
  • 报警升级：连续报警 N 次后升级通知（alert_upgrade 配置）
  • 日志记录：写入 alert_log 表，记录发送状态（SUCCESS/FAIL/FORBID）

消息模板

报警内容使用 Freemarker 模板渲染，支持变量占位符。模板存储在 rule.alert_template 字段或 alert_template 表中，支持 Text 和 Markdown 两种格式。模板可引用的上下文变量包括：

  • ${THRESHOLD} — 阈值
  • ${VERIFIED_BUCKETS} — 触发阈值的分桶列表
  • ${ALARM_NAME} / ${ALARM_DESCRIPTION} — 监控名称/描述
  • ${QUERY_STRING} — 查询语句
  • 各数据源返回的指标值（如 ${RESULT}、${BUCKETS} 等）

13安全分析

SSRF 风险（需重点关注） HTTP 数据源监控功能允许用户自定义 HTTP 请求地址，系统在服务端主动发起请求获取响应。这设计上具有 SSRF（服务端请求伪造）的潜在风险。系统定位为内网运维工具，强烈建议仅部署于企业内网，切勿对公网暴露。

安全建议

  1. 内网部署是基础：即使内网部署，HTTP 监控仍可能被用于探测内网其他服务。云服务器部署需防止访问云平台元数据服务。
  2. 最小权限原则：监控地址应精确固定，避免使用可由用户随意构造的动态 URL。
  3. 网络层控制：通过防火墙规则、代理网关或主机网络访问控制，约束服务出站请求范围。

已有的安全措施

  • JWT Token 鉴权（jjwt），接口需携带有效 Token
  • 支持 LDAP 对接企业账号体系
  • 数据隔离：部门-团队-用户三级权限，各团队数据互不可见
  • 数据库密码支持 Druid 加密（需自行配置）
  • 敏感信息加密处理（0.9 版本引入）
  • Log4j2 已升级至 2.17.1，修复 Log4Shell 漏洞

关键架构演进节点

2022-04-19：移除 xxl-job，自研调度引擎 这是项目最重要的架构决策之一。早期依赖外部 xxl-job-admin 服务做调度，部署复杂。kechangqing 借鉴 xxl-job 思想，用 MySQL 行锁 + 时间环（Time Ring）自研轻量调度引擎，内置于 monitor 服务中，从此单服务即可完成调度与执行，大幅降低部署门槛。
2022-03-29：移除 SPI 模块，架构内聚 早期有独立的 frostmourne-spi 模块负责消息发送。Aping 将其移除并内聚到 monitor 主服务，简化为当前的三模块结构（vue / common / monitor）。
2022-05：策略模式体系成型 一个月内密集接入 5 种数据源（PING/SkyWalking/Prometheus/IoTDB/Telnet）+ 环比规则 + 报警升级。这得益于 IMetric / IRule 策略接口的抽象设计，使得新增数据源只需新增实现类，验证了架构的可扩展性。
2021-12：Log4Shell 应急响应 Log4j2 漏洞爆发后，一个月内完成 2.16.0 → 2.17.0 → 2.17.1 三次紧急升级，体现了项目对安全事件的快速响应能力。

17总结与展望

项目优势

  • 低门槛：写一条查询即可完成监控配置，无需编写代码
  • 高扩展性：策略模式贯穿全程，新增数据源/报警方式只需新增实现类
  • 调度可靠：类 xxl-job 的调度引擎，快慢线程池隔离，misfire 补偿机制
  • 报警智能：静默、升级、恢复通知、时段控制，防止消息轰炸
  • 权限完善：三级组织模型 + 数据隔离 + LDAP 支持

待改进点

  • Spring Boot 版本较旧（2.3.1），可考虑升级至 2.7.x 或 3.x
  • 前端基于 Vue 2 + Element UI，可考虑升级至 Vue 3 + Element Plus
  • 调度依赖 MySQL 行锁，超大规模场景下可能成为瓶颈，可考虑引入 Redis 分布式锁
  • 缺乏程序自身日志采集与查询（已在规划中）
  • 国际化不完整（已在规划中）

总体评价 Frostmourne 是一个设计清晰、代码质量较高的开源监控项目。它巧妙地将"数据查询 + 规则判定 + 消息发送"三段式流程用策略模式解耦，调度引擎借鉴 xxl-job 的成熟方案，保证了可靠性。对于需要监控多种数据源、希望统一管理报警的团队，是一个值得深入使用和二次开发的优秀项目。
