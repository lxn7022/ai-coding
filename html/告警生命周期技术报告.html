摘要：先把三个生命周期拆开

“告警生命周期”这个词经常被当成一条流水线：产生 → 通知 → 处理 → 关闭。但在真实系统里，它其实是三条相互独立、通过 ID 关联的生命周期。把它们压进同一个 status 字段，是自研告警平台最常见、也最难回头的结构性错误。

  1. 检测、通知、事件是三层，不是一条状态流。检测层回答“条件是否成立”，通知层回答“该不该告诉谁”，事件层回答“谁在处理、何时算完”。三层各有自己的状态机、负责人和 SLA。
  2. 检测层的最小完备状态集是 inactive / pending / firing / resolved，外加与状态正交的“评估健康度”。无数据、查询失败、序列消失必须单独表达，不能混进 resolved。
  3. 抑制和静默不是状态，而是通知可见性维度。它们不该改变底层告警状态，否则抑制解除后无法正确恢复，也无法解释“为什么当时没通知”。
  4. 恢复路径与触发路径同等重要。没有恢复通知、恢复不受抑制约束、恢复判定不对称，是“告警不可信”的三大来源。
  5. 通知层要“至少一次 + 幂等”。去重键是 fingerprint，分组键是“路由 + group_by”，抑制是有向依赖，静默是有期限的匹配器。
  6. 事件层必须有 ack、升级超时、重开窗口和合并。ack 只停止升级，不等于修复；resolved（技术恢复）与 closed（确认闭环）应分离。

01

问题定义：为什么“生命周期”总是做错

先看一个并不罕见的夜间场景：磁盘使用率在 90% 阈值附近来回抖动，值班同学在 20 分钟里收到 12 条触发与恢复通知；他点了“认领”，指标随即恢复，但事件单仍挂在那里；第二天复盘时，系统里既说不清他真正开始处理的时间，也说不清这算一次故障还是六次。

这不是阈值调得不好，而是生命周期建模出了三个问题：状态语义重叠、层间边界缺失、恢复路径没有设计。阈值只是表象，状态机才是根因。

1.1 三个被混为一谈的生命周期

很多自研系统只有一个 alerts 表和一个 status 字段，取值为 pending / firing / acked / resolved / closed。这个设计在第一个月看起来很好用，随后会依次遇到下面这些无法回答的问题：

  • “ack 之后指标恢复了，状态该是什么？”——acked 是人的动作，resolved 是检测结果，两者不在一个维度上。
  • “静默期间恢复了，要不要发恢复通知？”——如果静默直接把状态改成 suppressed，底层状态已经丢了，恢复通知无从判断。
  • “规则删除了，还挂着的告警谁来关？”——没有“规则生命周期”与“实例生命周期”的区分，就会出现永远 firing 的僵尸告警。
  • “同一个服务 50 台机器同时故障，是 50 个事件还是 1 个？”——没有分组和事件聚合，通知风暴与事件碎片化同时发生。
  • “MTTR 到底从哪算到哪？”——没有明确的时间戳定义，指标只能靠猜。
状态爆炸的本质，通常不是状态太多，而是把“事实”“可见性”“人的动作”三个维度塞进了同一个枚举。

1.2 一条告警的完整旅程

下面用一条真实感足够强的时间线，把三层生命周期串起来。注意每个时刻“系统做了什么”和“人做了什么”是分开的——这正是后面数据模型要记录的东西。

  1. 检测支付服务的成功率跌破 99.5%，规则表达式首次命中。因为配置了 for: 5m，实例进入 pending，此时不通知。
  2. 检测连续 5 分钟满足条件，实例转为 firing，写入 firing_at，投递到通知流水线。
  3. 通知经过 30 秒 group_wait，同一服务的 6 条相关告警被合并为一个通知组，发给主值班。
  4. 事件值班人点击“认领”，事件从 triggered 变为 acknowledged，升级计时停止，MTTA = 5 分钟。
  5. 通知值班人把事件链接到排障频道，并静默了同机房另一条已知的连锁告警（30 分钟，带工单号）。
  6. 检测回滚完成后指标恢复，但配置了 keep_firing_for: 5m，实例继续保持 firing，避免瞬时恢复造成误判。
  7. 检测保持期结束，实例转为 resolved；因为此前发过触发通知，系统补发一条恢复通知，附带持续 34 分钟与峰值。
  8. 事件事件并未立即关闭：系统进入 10 分钟观察期，确认错误预算不再消耗后才自动 resolved；MTTR = 29 分钟。
  9. 事件值班人补充根因、影响面与行动项，事件 closed，并自动创建复盘任务。

这条时间线里至少有 5 个时间戳会被不同指标使用：active_at、firing_at、notified_at、acked_at、resolved_at。如果数据模型只存一个 created_at 和一个 updated_at，所有度量都会失真。

1.3 设计目标与硬约束

GOAL 01

可解释

任何时刻都能回答：为什么这条告警没通知？为什么通知了？为什么还没恢复？为什么事件关不掉？

GOAL 02

可恢复

进程重启、网络分区、下游限流之后，状态与通知都能收敛；重试不产生重复打扰，失败不会静默丢失。

GOAL 03

可审计

谁在何时认领、静默、改规则、关事件，都有不可篡改的时间线，能支撑复盘与合规。

GOAL 04

可治理

告警质量可度量、可比较、可回归；每条 P1 告警都有 owner、runbook 和测试。

GOAL 05

可扩展

多租户、多渠道、多区域；新增一个通知渠道或一种检测源，不需要改动状态机。

CONSTRAINT

三个硬约束

投递只能做到“至少一次”；状态存储是最终一致；通知有不可消除的端到端延迟。设计必须围绕这三点，而不是假设“恰好一次、强一致、实时”。

最容易踩的边界：ack 不等于 resolve

PagerDuty 的模型值得直接借鉴：告警（alert）只能被触发或恢复，不能被认领；事件（incident）才能被认领。认领只停止升级，不改变故障事实；如果认领超时仍未恢复，事件会回到 triggered 并继续升级。[6]

2.2 一个事件，多条告警：聚合关系怎么建

推荐用多对多关联表 incident_alert，而不是在告警表里放一个 incident_id。原因很现实：一条告警可能在事件合并时被转移到另一个事件；一个事件也可能在排障过程中不断纳入新的相关告警。多对多 + “当前有效关联”标记，可以保留完整的归属历史。

  • 首次关联：通知层成功发出第一条 P1/P2 通知时，以 dedup_key 查找打开中的事件；不存在则创建，存在则追加告警。
  • 合并：当两个打开中的事件被判定为同一故障（同服务、同根因、时间重叠），保留一个主事件，另一个置为 merged 并指向 merged_into。
  • 拆分：较少见，但排障中确实会发生（一个事件其实是两个独立故障）。拆分应新建事件并迁移关联，保留审计。

3.3 for 与 keep_firing_for：两个最容易被误用的参数

Prometheus 的 for 语义是：从第一次命中开始计时，期间每一次求值都必须继续满足，否则计时清零；满足时长达到 for 后才进入 firing。未达到之前的活跃状态就是 pending。[1]

prometheus/rules/payment.yamlyaml
# 触发条件与恢复条件成对设计：阈值滞回 + 持续时间 + 保持期
groups:
  - name: payment-slo
    rules:
      - alert: PaymentSuccessRateLow
        expr: |
          sum(rate(payment_requests_total{result="success"}[5m]))
          / sum(rate(payment_requests_total[5m])) < 0.995
        for: 5m                 # 连续 5 分钟低于 99.5% 才 firing
        keep_firing_for: 5m     # 恢复后再保持 5 分钟，抗抖动 / 抗数据缺口
        labels:
          severity: page
          service: payment-api
          team: payments
        annotations:
          summary: "支付成功率低于 SLO（当前 {{ $value | humanizePercentage }}）"
          runbook_url: https://runbooks.example.com/payment-success-rate
          dashboard_url: https://grafana.example.com/d/payment

合理用法

  • for ≥ 3 × 评估间隔，避免单点毛刺
  • 触发与恢复使用不同阈值（滞回），如 < 99.5% 触发、> 99.7% 恢复
  • keep_firing_for 用于桥接短暂数据缺口与抖动
  • 对“缓慢劣化”类指标，用更长窗口而不是更长 for

危险用法

  • for 远大于故障容忍时间，导致 100% 故障也要等半小时
  • 周期性强抖动场景：每次短暂恢复都会重置 for，可能永远不触发
  • 用 keep_firing_for 掩盖长期数据缺失
  • 把 for 当作“降噪”的唯一手段，而不治理指标本身

Google SRE Workbook 给过一个很尖锐的例子：一个 10 分钟 for 的规则，面对“每 10 分钟出现 5 分钟 100% 错误”的周期性故障，因为每次都在计时未满时恢复，永远不会告警，而这类故障在一天内会消耗约 35% 的月度错误预算。[4]这不是极端假设，很多批量任务和定时重试就是这个形状。

!
参数建议

for 取 3～10 倍评估间隔；keep_firing_for 取 for 的 0.5～1 倍；恢复判定再加一个独立观察期（如 5～10 分钟）。如果业务容忍时间小于这个组合，应该改用更高频的评估或 SLO 燃烧率，而不是把 for 调到 0。

3.4 恢复判定：对称性与观察期

绝大多数“告警不可信”的投诉，来自恢复路径设计得比触发路径草率。触发时精心设计了 for、多条件、抑制；恢复时却只看“这一秒表达式为空”。建议至少做三件事：

  1. 阈值滞回（hysteresis）。触发阈值和恢复阈值之间留出死区。例如 CPU 触发 > 90%，恢复 < 85%；成功率触发 < 99.5%，恢复 > 99.7%。
  2. 恢复保持期。用 keep_firing_for 或独立的 resolve_delay，让“刚恢复又掉下去”的抖动不产生一对无意义的触发 / 恢复通知。
  3. 影响面复核。对 P1/P2，不要只看单条指标。支付成功率恢复了，但队列积压仍在增长、错误预算仍在消耗，就不应关闭事件。

恢复通知的内容也应该认真设计：持续了多久、峰值是多少、影响范围、期间是谁处理的、有没有遗留风险。只发一句“已恢复”，等于把确认工作又推回给值班人。

i
一个容易忽略的细节

Alertmanager 的 group_wait（默认 30 秒）期间如果告警已经恢复，不会发送任何通知，这是刻意设计的降噪行为。[2]它与“恢复通知”不矛盾：前者是“还没发过触发通知”，后者是“已经发过触发通知，需要闭环”。实现时必须区分这两种情况。

3.5 抖动（flapping）识别与处置

抖动不是“告警太多”的同义词，它是一种可以被检测和量化的模式：在滑动窗口内，同一 fingerprint 的状态迁移次数超过阈值。建议在检测层就标记 flapping = true，而不是让值班人自己发现。

处置抖动时，优先顺序应该是：修指标 / 修阈值 → 加滞回 → 加保持期 → 降低通知级别 → 最后才是静默。直接静默只是把噪音藏起来，下一次换个人值班还会重演。

3.6 NoData / Error：评估健康度必须是一等公民

“没有数据”和“数据正常”是两件完全不同的事。Grafana 把这件事显式建模成两个额外状态：No Data（查询成功但无数据点）和 Error（查询失败或超时），并允许配置为 No Data、Alerting、Normal 或 Keep last state。[5]

最安全：采集断了本身就是要处理的事故。代价是采集系统抖动会放大成业务告警，需要单独的抑制与升级策略。

策略 B

保持最后状态

降噪：适合短暂的数据源抖动。风险是长时间失联时告警永远停在 firing 或 resolved，掩盖真实故障。

策略 C

标记 unknown

推荐默认：状态显式变为 unknown，并生成一条独立的“评估失联”元告警。原告警保留历史，不伪造恢复。

!
一个真实的坑：NoData 告警的标签不一样

Grafana 在进入 No Data / Error 时会创建独立的 DatasourceNoData / DatasourceError 告警实例，它们的标签集与原始告警不同，因此已有的静默、静默时段和通知策略可能不匹配。[5]自研系统如果采用类似设计，必须让元告警继承原始告警的 service、team 等路由标签，否则它会落到默认路由上。

04

通知生命周期：从事实到打扰

通知层做的不是“把告警发出去”，而是决定“此刻是否值得打扰一个人”。它需要去重、分组、抑制、静默、路由、限流、重试和升级，任何一环缺失，都会把成本转嫁给值班人。

4.1 去重：fingerprint 是整层的基石

一条告警的身份不是它的标题，也不是数据库自增 ID，而是标签集合的规范化哈希。Prometheus / Alertmanager 用 fingerprint 标识告警实例，并在 webhook 负载中回传。[2]自研系统应沿用同样的思路，并明确规范化规则，否则“同一条告警”在不同组件里会得到不同指纹。

internal/alert/fingerprint.gogo
// 规范化：排序 key、剔除空值、统一分隔符，避免 map 遍历顺序造成漂移。
func Fingerprint(labels map[string]string) string {
    keys := make([]string, 0, len(labels))
    for k, v := range labels {
        if v == "" { continue }   // 缺失与空值等价
        keys = append(keys, k)
    }
    sort.Strings(keys)

    h := sha256.New()
    for _, k := range keys {
        h.Write([]byte(k))
        h.Write([]byte{0xff})       // 分隔符，防止 "ab"+"c" 与 "a"+"bc" 碰撞
        h.Write([]byte(labels[k]))
        h.Write([]byte{0xff})
    }
    return hex.EncodeToString(h.Sum(nil))[:16]
}

标签设计决定了 fingerprint 是否稳定。下面这些值一旦进入标签，就会制造“永远无法恢复”的告警：

不要放进标签

  • request_id、trace_id、order_id
  • 带随机后缀的 Pod 名、容器 ID
  • 原始错误消息、SQL、URL query
  • 当前值、时间戳、通知次数
  • 用户 ID、手机号等敏感信息

适合放进标签

  • service、team、env
  • region、cluster、instance（稳定时）
  • severity、slo、alertname
  • runbook_url（作为 annotation 更合适）
  • 业务维度：tenant、plan（低基数）
i
episode：一次 firing 不等于一个告警

同一 fingerprint 恢复后再次触发，应视为新的 episode（episode += 1），而不是复用旧实例。这样既能保留历史，又能让“重开窗口”“复发率”“抖动率”有准确的时间边界。

4.2 分组：把 500 条告警变成 1 条可读的通知

分组的本质是“在时间窗口内，把共享同一组标签的告警合并成一条通知”。Alertmanager 的三个参数给出了很好的默认值，也揭示了核心权衡：[2]

表 4-1　分组参数与权衡（默认值来自 Alertmanager）

group_by[alertname, cluster]（示例）按哪些标签聚合通知更少、信息更粗通知更多、定位更细

三个实践要点：

  • 分组键必须包含路由。同一个标签组合可能命中不同 receiver（例如 P1 走电话、P3 走工单），如果 group key 不含 route，两个渠道会共用同一份节流状态，出现“电话没打、工单也没建”。
  • 给通知设置条数上限。一个组里 800 条告警对人不产生任何额外信息。建议单条通知最多展示 10～20 条，其余折叠为“还有 137 条同类告警”，并附查询链接。
  • group_interval 同时是发送超时。Alertmanager 文档明确：它也是每次发送的通知管道上下文超时；如果渠道很慢而 group_interval 很小，通知会被取消。[2]

4.3 抑制：用依赖关系代替人肉判断

抑制（inhibition）的语义是：当一组 source 告警存在时，静音一组 target 告警，两者在 equal 指定的标签上必须相等。它适合表达“上游故障导致的下游症状”，例如机房断电时，不必再收 300 台主机的实例告警。[2]

alertmanager/inhibit.yamlyaml
inhibit_rules:
  # 机房级故障 → 抑制其上的主机 / 实例级告警
  - source_matchers: [alertname="DatacenterDown", severity="critical"]
    target_matchers: [severity=~"warning|info"]
    equal: [region, datacenter]

  # 数据库主故障 → 抑制依赖它的服务告警
  - source_matchers: [alertname="DatabasePrimaryDown"]
    target_matchers: [alertname=~".*Latency.*|.*ErrorRate.*"]
    equal: [cluster, database]

抑制规则最容易出问题的地方不是语法，而是图结构：

  • 抑制环。A 抑制 B、B 抑制 A，最终两条都不通知。上线前应对规则做有向图建模，检测强连通分量（SCC），并限制抑制链深度（例如最多 3 层）。
  • 自抑制。Alertmanager 会阻止“同时匹配 source 和 target 的告警”被同类告警抑制，包括自己；但仍建议把 source 和 target 的匹配器设计成互斥，便于推理。[2]
  • 依赖来源。抑制关系应该由 CMDB、服务依赖图或 Kubernetes 拓扑自动生成，而不是靠人写死。人写的规则永远追不上架构变更。
  • 解除后的恢复。抑制只影响通知，不改变告警状态。抑制解除时，仍在 firing 的告警必须重新可见（必要时补一条摘要），否则会出现“故障还在，但再也没人收到通知”。

4.4 静默：必须有期限、有主人、有审计

静默是“我知道现在会响，先别响”。它和抑制的区别是：静默基于时间与匹配器，不需要另一个告警存在。一个可运营的静默至少要包含：

  • 强制到期时间，并设上限（如 7 天）。永久静默等于删除监控，只是没人敢承认。
  • 到期前提醒创建人，到期后自动失效；若是计划维护，应关联变更单。
  • 维护窗口结束生成摘要：窗口内抑制了多少条、其中多少条在窗口结束后仍在 firing。否则窗口会安静地掩盖一次真实故障。
  • 审计不可删：谁、何时、为什么静默，必须进入事件时间线。复盘时“当时为什么没收到告警”应该有确定答案。

4.5 路由：一棵可测试的匹配树

路由的本质是“标签匹配 → receiver”。设计要点不是支持多少种匹配语法，而是可预测：给定一组标签，任何人能手工推导出它会去哪。建议：

  • 树形结构，首个匹配生效，需要继续匹配时显式设置 continue；根节点必须有兜底 receiver。
  • 优先级用结构表达，而不是用规则顺序的隐式约定；禁止“靠写在前面”来抢优先级。
  • 提供 路由预演 API：输入 labels，返回命中的路由链、receiver、分组键与生效参数。这比文档可靠。
  • 路由变更走代码评审与灰度；生产环境的默认路由变更应该触发一次人工确认。

4.6 发送：至少一次，但看起来像恰好一次

通知投递的工程目标不是“绝不重复”，而是重复可接受、丢失不可接受、重复可识别。这要求幂等键、重试策略、失败队列和可见的投递状态。

4.7 升级与值班：确保总有人接住

升级策略（escalation policy）是通知层的最后一道保险。它的基本结构是“层级 + 等待时间 + 目标”：第 1 级主值班，5 分钟未认领升级到第 2 级，再 10 分钟升级到团队负责人。认领后停止升级；认领超时则回到 triggered 并继续升级。

!
无人在班 = 事件根本不会创建

PagerDuty 明确要求：只有升级策略上存在当前 on-call 用户时，事件才会被创建；如果排班存在覆盖缺口，事件不会触发。[6]自研系统如果照搬“有值班才通知”，必须额外提供兜底：排班缺口检测、团队频道广播、以及一条“值班覆盖率为空”的元告警。

一条合格的 P1 通知应该让人在 10 秒内回答：什么坏了、影响谁、从什么时候开始、现在多严重、我该先做什么、去哪里看。下面是一个内容模板的示意：

  • 三个数字足够。当前值、阈值、持续时间；更多细节放到链接里。
  • 动作必须可点。大盘、Runbook、认领、静默，缺一不可；静默要带默认时长与原因输入。
  • 同一事件用线程更新。后续进展回复在原消息线程里，而不是每条都新发一条；否则一次故障会刷屏整个频道。
05

事件生命周期：让人和系统都闭环

检测层告诉你“有事发生”，通知层确保“有人知道”，事件层负责“有人处理、有记录、有结论”。事件不是告警的附属品，它有自己的状态、升级规则和复盘要求。

triggered → acknowledged → resolved → closed

旁路：escalated 升级、reopened 重开、merged 合并。ack 只停止升级，不改变故障事实。

5.1 状态定义

表 5-1　事件状态与语义

triggered已创建，尚无人认领，升级计时进行中告警首次成功通知 / 人工声明认领、升级、恢复按升级策略持续触达

5.2 ack 的语义：停止升级，不等于修复

ack 是“我看到了，我来处理”，它解决的是注意力归属问题，不是技术问题。因此：

  • ack 必须绑定人。记录 acked_by、acked_at、ack_channel；广播给同组值班，避免两个人同时扑上去。
  • ack 有超时。例如 15 分钟没有任何操作，自动回到 triggered 并继续升级；否则一个误点就能让事件静默到天亮。
  • ack 不抑制恢复通知。恢复仍然要通知，并且要告诉原认领人“已经恢复了，你可以停止处理”。
  • 并发认领用乐观锁。UPDATE ... WHERE status='triggered'，失败者收到“已被 XXX 认领”，而不是静默失败。

5.3 自动恢复与人工关闭之间，隔着一个观察期

“所有关联告警都 resolved 了”是必要条件，不是充分条件。缓存可能还在返旧数据，队列可能还在积压，客户端重试可能还在放大流量。建议的自动恢复条件是：

AUTO RESOLVE CONDITION all(linked_alerts.state == resolved)
AND now - last_alert_resolved_at >= hold_down（建议 5～15 分钟）
AND 关键 SLI 在观察窗口内未再消耗错误预算
AND 没有关联的进行中变更 / 维护窗口

不满足时，事件保持 acknowledged，并提示“指标已恢复，等待观察期确认”。这比“指标一好就自动关闭、十分钟后又重开”体验好得多。

5.4 重开窗口与事件合并

抖动不仅制造通知噪音，也制造事件碎片。两个机制可以显著改善：

  • 重开窗口（reopen window）。事件 resolved 后 N 分钟内（如 30 分钟），同 dedup_key 再次触发时，不新建事件，而是把原事件置为 reopened，保留原时间线与负责人。N 分钟后再触发则新建，并链接到前一个事件。
  • 事件合并（merge）。同一服务、同一时间段、疑似同根因的多个事件，允许合并为一个主事件。被合并事件保留只读时间线与 merged_into 指针，避免“关了一个，另一个还在响”。
i
dedup_key 怎么设计

不要直接用 fingerprint：一个事件往往聚合多条告警。建议用 hash(service, env, incident_type, time_bucket)，其中 time_bucket 按故障类型取 30 分钟到 6 小时。这样既能合并同一故障的多个症状，又不会把一周内的两次独立故障粘在一起。

5.5 协作：角色、时间线与战情室

Google SRE 的事件管理实践强调明确的角色分工：事件指挥官（IC）负责决策与协调，操作负责人（OL）负责动手，沟通负责人（CL）负责对内对外同步。[8]小团队可以一人兼任，但角色必须显式，否则会出现“所有人都在查日志，没人对外同步”。

事件时间线应该自动记录，而不是靠人补：状态变更、通知发送、ack、升级、评论、关联告警、加入/退出、变更单、恢复、关闭。时间线是复盘的主要输入，也是回答“当时到底发生了什么”的唯一可靠来源。

5.6 复盘：把一次故障变成系统能力

复盘（postmortem）的目标不是追责，而是找到系统性改进点。一个可执行的最小闭环：

  1. 触发条件：P1/P2、MTTR 超阈值、重复故障、有客户影响、或值班人主动要求。
  2. 自动生成初稿：时间线、影响面、相关告警、参与人、变更记录，全部从系统拉取。
  3. 无责讨论：聚焦“系统为什么允许这件事发生”，而不是“谁点错了按钮”。
  4. 行动项：每条必须有 owner、截止日期、优先级，并进入 issue tracker；下一轮复盘首先检查上轮行动项完成率。
  5. 回写检测：新增/调整告警规则、抑制规则、Runbook；否则同样的故障下次仍然靠人肉发现。

6.3 事件溯源与 Outbox

“当前状态”和“状态变更事实”是两份数据。前者让查询快，后者让系统可解释。推荐的做法是：

  • 状态变更与 alert_event 在同一个数据库事务中完成；当前表可以被视为事件表的物化视图。
  • 需要对外发消息时，不直接调用 Kafka，而是写 outbox 表；由 CDC / 轮询发布器投递。这样“状态改了但消息没发”与“消息发了但状态没改”都不会发生。
  • 事件表按 occurred_at 分区（按天或按月），保留期结束后归档到对象存储；审计需求通常要求 1 年以上。

6.5 标签规范与多租户

标签既是查询维度，也是路由依据，还是 fingerprint 的输入。建议在入库时做强制校验，而不是靠文档约定：

  • 白名单 + 基数上限：每个租户允许的标签 key 固定；单个 key 的取值基数超过阈值（如 10 万）直接拒绝并告警。
  • 保留标签：tenant、service、env、region、severity、team、alertname 由平台注入，业务不可覆盖。
  • 租户隔离：所有查询强制带 tenant_id；数据库可用行级安全（RLS）兜底，应用层再做一次校验。
  • 配额：每租户的规则数、活跃实例数、通知量、静默数都要有上限；否则一个租户的配置错误会拖垮整个平台。

7.2 端到端数据流

  1. 采集与规范化：统一标签、单位、时间戳；丢弃高基数与非法标签，并记录丢弃原因。
  2. 评估：按 hash(rule_id) 分片；每个分片维护水位线，输出“某个 fingerprint 在某个时刻的状态”。
  3. 状态写入：CAS 更新当前实例，同事务追加 alert_event 与 outbox。
  4. 降噪：去重 → 分组 → 抑制 / 静默 → 路由；每一步都可解释地记录“为什么被丢弃”。
  5. 投递：按渠道优先级排队，幂等发送，记录回执；失败进入重试与死信队列。
  6. 事件：首次成功通知后创建/关联事件；ack、升级、恢复、关闭都写时间线。
  7. 闭环：复盘、行动项、规则调整；质量指标回流到规则评审。

7.3 一致性与高可用

告警系统不应该追求“恰好一次”，而应该追求不丢、可去重、可解释。这三年被反复验证的结论，在 Alertmanager 的 HA 设计里体现得很直接：gossip 复制静默与通知日志，网络分区时选择 fail-open，宁可重复通知也不漏报；Prometheus 应把告警发给所有 Alertmanager 实例，而不是走负载均衡。[3]

WRITE PATH

单写者 + 幂等

以 fingerprint 作为 Kafka 分区键，保证同一告警实例只有一个消费者写入；状态更新带 version 做 CAS；重复消息由 (alert_id, episode, to_state, occurred_at) 唯一约束吸收。

READ PATH

当前表 + 事件表

当前表服务查询与判定，事件表服务审计与重放。两者在同一事务更新；如果当前表损坏，可以从事件表重建到任意时间点。

DELIVERY

至少一次 + 幂等键

发送失败可重试；重复发送由渠道侧或幂等键去重。跨副本重复用“通知日志 + 错峰等待”收敛，参考 Alertmanager 的 peer position 机制。

PARTITION

fail-open，而非静默

网络分区时，允许重复通知，不允许漏报。分区恢复后，静默与通知日志按时间戳合并，后续通知重新去重。

!
不要把“高可用”做成“双写”

两个评估副本同时写同一 fingerprint，会产生两次 firing、两次通知，甚至状态互相覆盖。正确做法是分片（每个 fingerprint 只有一个 owner）或选主；副本只做热备，不参与写。

边界与一致性：真正难的是这些情况

正常路径的状态机只是及格线。乱序、重复、风暴、时钟、规则变更、重启——这些边界才决定系统在生产环境里是否可信。

8.1 事件时间与处理时间

告警评估通常基于“事件时间”（指标采样时刻），而状态写入基于“处理时间”。两者可能相差数秒到数分钟，尤其在补数、重放、跨区域传输时。建议：

  • 所有状态判定使用事件时间，并维护水位线 watermark = max(event_time) - allowed_lateness。
  • 迟到但在允许范围内的数据，允许修正最近一次状态；超出范围的迟到数据只记录、不回写状态，并计入 late_dropped 指标。
  • 绝不能用处理时间判断“持续了多久”，否则一次消费积压就会制造大量假恢复或假触发。

8.2 重复、乱序与幂等

消息队列通常保证至少一次，重复不可避免。状态机需要满足幂等：同一迁移重复执行，结果不变。实现上分两层：

  • 数据库层：唯一约束 (alert_id, episode, to_state, occurred_at) 吸收重复事件；状态更新用 WHERE version = ? 做 CAS。
  • 业务层：迁移函数只接受合法前置状态（如只有 firing 才能转 resolved），非法迁移记录为 ignored 而不是报错。

8.3 告警风暴

风暴的根因通常不是“告警太多”，而是一个故障产生了大量同构告警。处置顺序应该是：抑制根因 → 分组聚合 → 限流 → 降级为摘要 → 最后才人工静默。

PROTECT

平台侧保护

按租户 / 服务 / 渠道设配额；P1 预留独立配额；队列分级，低级别可延迟；单组通知条数上限；模板渲染失败不阻塞队列。

INFORM

给人可行动的信息

风暴时只发一条“聚合摘要”，说明影响范围、疑似根因、已抑制数量，并附完整列表链接；不要让人在 500 条消息里找第一条。

8.4 级联故障与抑制深度

级联抑制的目标是“只让人看到根因”，但过度抑制会让人看不到真正需要处理的次生故障。建议：

  • 依赖图来自 CMDB / 服务拓扑，而不是手工规则；变更时自动更新。
  • 限制抑制链深度（如 3 层），并对“被抑制的 P1”单独计数；如果 P1 被抑制，必须有摘要通知。
  • 抑制规则变更走评审，并在预发环境用历史告警回放验证。

8.5 时区、时钟与夏令时

  • 存储统一 UTC；展示按租户时区；不要在数据库里存本地时间。
  • 持续时间用单调时钟计算，避免 NTP 回拨导致负时长。
  • 静默时段如果使用 time_intervals，必须显式指定 location；否则默认 UTC，跨时区团队会在错误的时间安静。
  • 对夏令时切换日，周期任务与“每日摘要”要做一次专项测试。

  • 启动宽限期：重启后不要立刻对“刚加载的旧状态”重发通知；用 1～2 个评估周期做状态对齐。
  • 不重放历史通知：重放事件表只用于重建状态，不应触发真实发送；发送侧要有 replay=false 的保护。
  • 滚动升级：分片迁移时先让新实例接管只读，再切换写入；切换窗口内对同一 fingerprint 保持单写者。
  • 规则热加载：加载失败必须保留旧版本并告警，不能“配置错误 → 全部规则消失 → 所有告警恢复”。
09

告警质量：从“响了多少次”到“值不值得响”

告警系统的产出不是通知数量，而是可行动的信号。衡量它需要同时看准确率、召回率、检测速度和恢复速度，单看任何一个都会被指标游戏带偏。

9.1 四个质量维度

Google SRE Workbook 用四个参数评价告警策略，这套框架同样适用于单条规则和整个平台：[4]

Precision 精确率

发出的告警中，真正重要（需要行动）的比例。低精确率 = 狼来了。

Recall 召回率

重要事件中被检测到的比例。低召回率 = 漏报，通常更危险。

Detection 检测时延

从故障发生到通知送达的时间。它直接消耗错误预算。

Reset 恢复时延

故障恢复后告警仍持续的时间。过长会让人忽略后续告警。

9.3 告警评审：每周 30 分钟，砍掉噪音

治理不是一次性项目，而是固定节奏：

  • 每周：看 Top 10 最吵的告警（按通知数、按人数、按重复次数），逐条决定“修阈值 / 加抑制 / 降级 / 删除”。
  • 每月：审查告警目录，检查 owner、runbook、severity 是否仍然有效；清理无人负责的规则。
  • 每季度：复核 SLO 与阈值；用历史数据回放，评估如果调整参数会少发多少、漏掉多少。
  • 每次 P1 复盘：必须回答“告警是否及时、是否准确、通知是否到达对的人”，并产出至少一条检测层改进。

发布策略建议三级：shadow（只记录不通知，观察一周）→ canary（单租户 / 单集群生效）→ full。删除规则时，先在 shadow 模式下确认没有活跃实例，再执行。

9.5 告警预算

把“值班注意力”当成一种有限预算：每个班次最多 2 次 P1 打扰、10 次 P2。超预算不是值班人的问题，而是告警组合的问题。这个机制的好处是把“降噪”从口号变成可执行的约束：当新增一条 P1 规则时，必须说明它将挤占哪一部分预算，或者同时下线一条低价值规则。

10

SLO 与燃烧率：检测层的上游现代化

阈值告警回答“某个指标是否越界”，SLO 告警回答“用户是否正在失去可靠性”。前者适合定位，后者适合决定要不要半夜叫醒一个人。两者是分层关系，不是替代关系。

10.1 为什么阈值告警不够

  • 阈值与影响脱节。CPU 80% 可能毫无影响，成功率 99.6% 可能已经在快速消耗预算。
  • 精确率低。固定阈值在低流量时段极其敏感，一次失败请求就能触发。
  • 无法排序。十个阈值同时越界时，无法判断哪个更值得先处理。
  • 恢复慢。长窗口阈值告警在故障恢复后仍持续很久，制造“狼来了”。

10.2 燃烧率：把错误预算变成速度

燃烧率（burn rate）是“当前错误率相对于 SLO 允许错误率的倍数”。燃烧率为 1，表示按当前速度刚好在 SLO 周期结束时用完预算；燃烧率为 14.4，表示 1 小时就消耗掉 2% 的月度预算。

BURN RATE burn_rate = error_rate ÷ (1 − SLO)
time_to_exhaustion = SLO_window ÷ burn_rate

EXAMPLE · 99.9% SLO / 30 天 error_rate = 0.1% → burn_rate = 1 → 30 天耗尽
error_rate = 1% → burn_rate = 10 → 3 天耗尽
error_rate = 100% → burn_rate = 1000 → 约 43 分钟耗尽

10.3 多窗口、多燃烧率

单窗口燃烧率仍然要在“检测快”和“恢复快”之间二选一。多窗口方案用长窗口保证精确率、短窗口保证恢复速度，两者同时超阈值才触发。经验法则是短窗口取长窗口的 1/12。[4]

10.4 低流量服务的四个陷阱

SRE Workbook 专门警告：低流量下，单次失败就能造成很高的“错误率”，从而误触发高燃烧率告警。可选对策：

  1. 合成流量：用探针 / 黑盒监控制造稳定分母，但要意识到它可能掩盖真实用户路径的故障。
  2. 合并服务：把同一故障域的小服务合并成一个 SLI，降低单点噪声。
  3. 调整 SLO 或窗口：承认单次失败的业务影响，不要用 99.99% 的目标去要求一个低频接口。
  4. 加最小请求数门槛：请求数低于阈值时，不触发燃烧率告警，改用可用性探测或人工巡检。

11.1 三条可复用的结论

LESSON 01

检测与通知必须分离

规则引擎只对“事实”负责；分组、抑制、路由、重试是另一个服务的事。合在一起会让规则配置承担它不该承担的复杂度。

LESSON 02

评估健康度要显式

无数据、查询失败、序列消失是第三种事实，不是“正常”也不是“恢复”。给它一个状态，系统才诚实。

LESSON 03

通知之上还要有事件

通知解决“知道”，事件解决“负责”。没有事件层，ack、升级、MTTA、复盘都无处安放。
